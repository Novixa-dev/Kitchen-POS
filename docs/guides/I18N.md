# Internationalisation

Kitchen POS ships Arabic (default) and English. This is how the layer works and
how to extend it.

---

## Design

Zero runtime dependencies. The whole layer is `frontend/src/i18n/`:

| File | Responsibility |
|---|---|
| `locales/en.ts` | **Canonical dictionary.** Defines the key set |
| `locales/ar.ts` | Arabic, typed as `Dictionary` — must cover every key |
| `types.ts` | `Locale`, `Direction`, `TranslationKey`, locale metadata |
| `translate.ts` | Pure lookup, interpolation, CLDR plurals. No React |
| `format.ts` | `Intl`-based number, currency, date, time, elapsed formatting |
| `context.ts` | The context object and its value type |
| `I18nProvider.tsx` | Provider: locale state, persistence, `<html>` attributes |
| `useI18n.ts` | The hook components use |
| `standalone.ts` | `t()` for code that runs outside the provider |

### Why `en.ts` is canonical

`TranslationKey` is derived from `typeof en`, and `ar.ts` is declared as
`Dictionary = Record<TranslationKey, string>`. A missing or misspelled Arabic
key is therefore a **compile error**, not a string that silently renders as its
own key. A dictionary-parity test asserts the same thing at runtime, plus
placeholder consistency between locales.

### Why `Intl` and not a library

`Intl` is part of the JavaScript runtime, so nothing is fetched and nothing is
bundled. That matters for an offline-first app: a CDN-loaded locale pack would
be a runtime network dependency, which the product promises not to have.

## Using it

```tsx
import { useI18n } from '../../i18n/useI18n';

const MyComponent = () => {
  const { t, tPlural, formatCurrency, formatDate, locale, dir } = useI18n();

  return (
    <div>
      <h1>{t('page.reports')}</h1>
      <p>{t('auth.loggedInAs', { name: staff.name })}</p>
      <p>{tPlural('order.itemCount', cart.length)}</p>
      <p className="tabular">{formatCurrency(total)}</p>
      <p>{formatDate(bill.created_at, 'medium')}</p>
    </div>
  );
};
```

What the hook gives you:

| Member | Purpose |
|---|---|
| `t(key, values?)` | Translate; `{placeholder}` substitution |
| `tPlural(base, count, values?)` | CLDR plural selection; injects `{count}` |
| `locale` / `dir` | `'ar' \| 'en'` and `'rtl' \| 'ltr'` |
| `setLocale` / `setNumerals` | Change and persist |
| `currency` | The configured currency, for building labels like `Price (ر.س)` |
| `formatNumber` / `formatCurrency` / `formatPercent` | Numeric formatting |
| `formatDate` / `formatTime` / `formatDateTime` | `'short' \| 'medium' \| 'long' \| 'weekday' \| 'monthYear'` |
| `formatRelativeTime` / `formatElapsed` | "5 minutes ago" / `MM:SS` |

### Outside the provider

Error boundaries sit **above** the i18n provider — if the provider is what
threw, calling `useI18n()` in the fallback would throw again and leave a blank
screen. Those use the standalone translator, which reads the locale from
`<html lang>`:

```tsx
import { tStandalone as t } from '../../i18n/standalone';
```

## Adding a string

1. Add the key to `locales/en.ts`, in the section it belongs to.
2. Add the same key to `locales/ar.ts`. TypeScript will tell you if you forget.
3. Use it through `t()`.

Key naming: `domain.thing` or `domain.thing.detail`. Reuse the generic
namespaces — `action.*`, `label.*`, `state.*`, `validation.*`, `a11y.*` —
rather than adding `myPage.save`.

### Plurals

Arabic has **six** CLDR plural categories against English's two:

| Category | Arabic applies to | English applies to |
|---|---|---|
| `zero` | 0 | — |
| `one` | 1 | 1 |
| `two` | 2 | — |
| `few` | 3–10, 103–110, … | — |
| `many` | 11–99, 111–199, … | — |
| `other` | everything else | everything but 1 |

So `count === 1 ? 'item' : 'items'` is wrong in Arabic for 0, 2, 3–10 and
11–99. Declare the full set and let `Intl.PluralRules` choose:

```ts
// en.ts
'cart.items.one':   '{count} item',
'cart.items.other': '{count} items',

// ar.ts
'cart.items.zero':  'لا توجد أصناف',
'cart.items.one':   'صنف واحد',
'cart.items.two':   'صنفان',
'cart.items.few':   '{count} أصناف',
'cart.items.many':  '{count} صنفًا',
'cart.items.other': '{count} صنف',
```

```tsx
tPlural('cart.items', count)
```

`.other` is the required fallback. Note that the dual and singular forms spell
the number out, so they legitimately omit `{count}` — the parity test allows
that for `.zero`, `.one` and `.two`.

### Values that live in the database

Enum-like values stored in SQLite — expense categories, staff roles,
preparation statuses, payment methods — keep their **English stored value** and
translate only the display. Rewriting them would orphan historical rows and
break permission checks. The pattern is a lookup with a raw-value fallback:

- `frontend/src/pages/Expenses/expenseCategories.ts`
- `frontend/src/pages/Staff/staffRoles.ts`

## RTL

Switching locale sets `dir` on `<html>`; everything else follows from CSS
logical properties.

### Use logical utilities, always

| Instead of | Use |
|---|---|
| `ml-2` / `mr-2` | `ms-2` / `me-2` |
| `pl-4` / `pr-4` | `ps-4` / `pe-4` |
| `left-0` / `right-0` | `start-0` / `end-0` |
| `text-left` / `text-right` | `text-start` / `text-end` |
| `border-l` / `border-r` | `border-s` / `border-e` |
| `marginLeft` (inline style) | `marginInlineStart` |
| `rounded-l-*` | `rounded-s-*` |

### What stays LTR on purpose

Some things are physical conventions, not running text, and must **not** mirror.
Pin them with `dir="ltr"`:

- Numeric keypads — `1 2 3` top-left is muscle memory
- PIN progress dots — they fill in entry order
- Clocks and `hh:mm` timers — otherwise `03:45` reads as `45:03`
- Signed percentages, so the sign stays attached to the number
- Stack traces and other code

### Directional icons

Chevrons, arrows and "back" glyphs point the wrong way under RTL. Add
`rtl-flip` to the icon (not its container):

```tsx
<SvgIcon name="caret-right" className="rtl-flip" />
```

Non-directional icons — a trash can, a printer — must **not** be flipped.

### Typography

Arabic glyphs sit lower and need more leading than Latin at the same size, so
`:root[data-locale="ar"] body` gets `line-height: 1.7`. Arabic is never
italicised: `em`/`i` are reset to upright semibold under the Arabic locale.

Price columns carry `.tabular` (`font-variant-numeric: tabular-nums`) so
proportional digits cannot make a column of numbers ragged.

## Numeral systems

Independent of the language. Both locales can render Latin (`0-9`) or
Arabic-Indic (`٠-٩`) digits, selected in Settings → Language & region and
applied by appending `-u-nu-latn` / `-u-nu-arab` to the `Intl` locale tag.

**The default is Latin, even in Arabic.** Operators read prices faster in Latin
digits, and they match what payment terminals and most receipt printers show.
Arabic-Indic is available for outlets that prefer it.

## Adding a locale

1. Add the code to `LOCALES` and an entry to `LOCALE_META` in `types.ts` —
   BCP-47 tag, direction, native name.
2. Create `locales/<code>.ts` typed as `Dictionary`. TypeScript lists every
   missing key.
3. Mirror it in `backend/src/services/receipt.ts` (`RECEIPT_COPY`) and in
   `backend/src/lib/settings.ts` (`Locale`), so receipts and the settings
   schema know about it.
4. The locale appears in the switcher, the setup wizard and Settings
   automatically.
5. If it is RTL, confirm the "stays LTR" list above still holds.

## Fonts

No webfont is fetched — that would be a runtime network dependency. The stack
in `index.css` covers Arabic and Latin from what each OS already ships:

```
"Segoe UI", "SF Arabic", "Noto Sans Arabic", "Noto Kufi Arabic",
Tahoma, "Helvetica Neue", Arial, system-ui, sans-serif
```

To bundle a font instead, add the file under `frontend/public/fonts/`, declare
an `@font-face` in `index.css`, and put the family first in `--font-sans`.
Receipts use their own stack in `receipt.ts` and would need the same change.

## Tests

`frontend/src/i18n/__tests__/` covers:

- **Dictionary parity** — Arabic and English define exactly the same keys
- **No blank translations** in any locale
- **Placeholder parity** — `{name}` in one locale implies `{name}` in the other
- **Arabic default** is asserted, so it cannot regress silently
- **Plural categories** — zero / one / two / few / many are each exercised
- **Formatters** — currency placement and precision, both numeral systems,
  date and elapsed-time edge cases, invalid input

Run them with:

```bash
npx vitest run src/i18n --prefix frontend
```
